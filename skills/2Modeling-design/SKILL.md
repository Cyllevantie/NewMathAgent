## 必须产出

在当前工作目录的 `reports/` 子目录中创建或更新：

- `reports/ANALYSIS_MODELING_REPORT.md`：
  - 赛题分析、子问题拆解、数据与附件理解、评价标准、关键歧义和假设预检。
  - 逐子问题给出：变量与符号、模型假设、决策变量 / 目标函数 / 约束条件（建模三要素显式写出）、求解算法、机理依据（引用文献方向）、实现口径、代码阶段任务清单。
  - 求解算法选型：黑箱/非凸/不可导/组合优化类子问题，可标注"用 `metaheuristic-optimization` skill（MEALPY：GA/PSO/DE/GWO/WOA）"；线性/凸/可精确求解的问题优先用专用求解器（scipy/Gurobi），不强行套用元启发式。
  - 每个关键假设/建模决策附一行"为什么"，让评审员能据以判断是否偏离题意/机理。
  - 报告带版本号与修订历史（评审回执如何被吸收）。
- `reports/TASK_CONTRACT.json`（启用 content-quality 时必写：项目根存在 `docs/CONTENT_QUALITY.md` / `config/content_quality.json`；schema 见前者「题意契约」）：
  - 把题面每条硬条件与交付要求映射为一个 requirement：`{id, source:{file,quote}, source_semantics, model_semantics, model_anchor:{file,quote}, status:"mapped"}`。
  - `source.quote` 必须是 `request/` 下文件（题面/附件说明）中逐字存在的原文（子串匹配，照抄含标点，别改简繁/空格）；`model_anchor.quote` 指向本报告里对应模型定义的原文。
  - `source_semantics`/`model_semantics` 各含 `quantifier/scope/unit/time_reference`，如实写"题面语义"与"你模型实际语义"并保证一致；程序只查两端一致，评审会独立对照原文，不许两端一起填错蒙混。
  - **禁止弱化**：题面"所有子单元/覆盖全部面积"不得写成"至少一个/发生过一次"；累计面积不等价于空间覆盖。随机量写清基期、是水平还是增量、是否逐年累积、跨期依赖（例：题面"每年相对 2023 约 ±5%"是固定基期波动，不是上一年连乘）。
  - status 填 `mapped` 的项其锚点必须真实有效；变化时更新锚点，不得保留失效原文引用。

### 任务覆盖与证据边界

逐项回答题面明确要求，并区分“有数据支持的结果”“附带假设的情景方案”“当前无法识别的量”。不得为了凑交付粒度编造阈值、强行分组或夸大统计证据。

- 题面明确指定的格式和交付粒度须覆盖；缺数据或缺模板时记录缺口、影响与可完成的部分，不把自制文件冒充指定模板。
- 证据不足时，说明原因；能够给出条件方案时明确假设、适用范围和验证限制。确实不可识别时允许报告不可识别及需要补充的数据，不能给无依据的确定结论。
- 简单模型、不分组、负结果或边界解不自动视为失败。与适当基线比较，核对题面约束和实现；符合题意且证据支持就保留。
- 对未覆盖的题面要求给出具体原因和补救方式，评审区分“遗漏/未尝试”和“经分析确有证据限制”。

不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。


## 工作流程


### Step 0（前置）：题面硬约束与交付契约清单

动手拆题前，先在 `ANALYSIS_MODELING_REPORT.md` 开头写一小节”题面硬约束与交付契约”，逐条列出**任何模型都不得违反**的边界 + **必须交付**的东西，建模全程以此为锚、防漂移：

- 硬约束（候选不得破坏）：题面给定的物理定律/几何关系/数值常量（如速度范围、间隔下限、尺寸/半径）、数据给定条件、格式/单位要求、可行性要求。
- 不可违反项：不允许通过绕过题意、忽略数据、改口径来”做出来”。
- 交付边界：本题要求交什么（如特定模板/表/文件、指定格式的数值），哪些研究材料留内部不进论文。
- 附一行”为什么”给每类约束（为什么它是硬的、违了会怎样），供评审核对。

每个子问题建模时都对照本清单自查：模型/解是否仍满足硬约束、是否覆盖了交付项。发现题面某处理解有歧义、需放宽某约束时，在假设预检里显式记录并给依据，而不是悄悄忽略。

### Step 1: 子问题拆解

只把题面中明确编号的顶层问题当作子问题，例如”问题一/二/三””Problem 1/2/3”。不要把小问、背景描述、数据说明、提交要求误当成独立子问题。

在 `ANALYSIS_MODELING_REPORT.md` 开头明确写：

根据题目动态调整问题数量

本赛题共 X 个子问题。

每个子问题要说明：

- 输入数据和已知条件。
- 决策变量或预测对象。
- 目标函数或评价指标。
- 约束条件。
- 与其它子问题的依赖关系。
- 绘制哪些图像或表格来展示结果。

### Step 2: 假设敏感性预检

列出关键歧义，不要急着定模型。对影响结果的歧义至少给出两种解释，并用简单验算或逻辑递进判断选择。

必须在 `ANALYSIS_MODELING_REPORT.md` 中包含：

```markdown
## 假设敏感性预检

### 模糊表述及解释
...

### 快速验算与递进性检查
...

### 最终采用的解释
...

### 绘制的图像和对比表格


```

如果某个假设会让后续问题的新增条件没有边际效果，要回头调整解释.

可行域截断审计（防"自设假设卡掉更好解而不自知"）：凡是缩小了可行域/解空间的建模假设或决策（τ 下界、整机指派/一机只服务一目标、每机≤N 弹、固定航路/走廊、离散格点、忽略可穿插/可拆分等），必须在建模报告里给它单独一行"截断审计"：①明确写出它排除了哪些本可存在的策略族；②预期代价 + 复算/复核计划（在哪一步做"去掉该假设的粗重优"并报告 Δ）；③若该假设纯为求解便利（非题意/非物理硬约束），必须标注并在 6Robustness 兑现松弛审计。**不许**把"工程简化"当"题面约束"写，也**不许**只披露不审计。优化题的最终结论须能说清"在全空间/在假设结构内"：只有假设结构内的，才称结构内最优；全空间结论要有相应审计支撑或明说未覆盖。

### Step 3: 数据理解与建模路线

对每份附件做数据理解：

- 行列规模和字段解释。
- 缺失、异常、重复、单位不一致。
- 可直接用于建模的变量。
- 需要派生的指标。

然后给出总体路线：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> 。。。。 -> 结果检验 -> 论文展示
```

### Step 4: 建模报告

在 `ANALYSIS_MODELING_REPORT.md` 中写出可交给代码阶段实现的完整方案。

每个子问题至少包含：

- 问题目标。
- 符号和变量。
- 模型假设。
- 目标函数。
- 约束条件。
- 求解方法。
- 输入输出。
- 代码实现要点。
- 结果校验方法。

公式要清楚到代码阶段能直接实现。算法描述要包含核心步骤、停止条件、复杂度或可行性说明。

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 数据处理方案
## 3. 符号说明
## 4. 问题一模型
## 5. 问题二模型
## 6. 问题三模型
    .... 
## 7. 灵敏度分析与检验方案
## 8. 代码实现任务清单
```

如果子问题数量不是 3 个，按实际题面调整章节，不要硬凑。

### Step 5: 给代码阶段的接口

在 `ANALYSIS_MODELING_REPORT.md` 末尾写一个“代码实现任务清单”，格式如下：

```markdown
## 代码实现任务清单

| 任务 | 输入 | 输出 | 方法 | 校验 |
| --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... |
```


## 质量要求

- 所有结论都能回到题面或数据。
- 不编造数据字段和数值。
- 不跳过歧义分析。
- 模型既要有数学表达，也要能被代码实现。
- 若数据不足或题面不清，要明确记录风险和替代方案。

### 数学结构与理论精简（进代码前先"找结构"，避免纯蛮力/纯枚举）

竞赛高分常来自一个能缩小搜索/证明结论的结构性观察，而不仅是"枚举完整、数值对上"。每个子问题在设计数值方法前，先做一轮数学结构挖掘，在建模报告里给"理论精简"小节：

1. 找可证结构：单调性（最优解随参数单调 → 可二分/单调栈）、凸性/凹性、可分性（多目标能否解耦成子问题）、对称性、对偶、或题目域上的已知结论。能证的写成一两条引理/命题 + 证明要点，并说明它如何被用到（缩小搜索、保证全局最优、或给出剪枝依据）——"没被用到的定理"是装饰，不算数。
2. 几何/物理判据给解析依据：判据若用离散采样/枚举判定，给一个"为何采样充分/为何检查这些边界点就够"的解析论证（凸体、单调性、最坏情形），而不是只堆采样档数。
3. 诚实标注不可约处：若某子部分确无结构可挖掘、只能枚举/启发式，显式说明"为何不可被结构简化"，并给出你已利用的剪枝/上界依据。
4. 每个理论声明标"确定性"：哪些是可证命题（给证明要点）、哪些是数值发现的规律（标为观察/经验，不作定理宣称）——防"编一个看似定理的假命题"。证明要点必须步骤自洽、能被 4review 的 review-math 逐行复核。

### ② 返修台账（被门禁退回过的轮次必做）

```bash
python lib/web/check_receipts.py
```

病灶：返修记录里写「§15.1 该句改『≤0.98%』」，而**那句话本身就是 `≤0.98%` 的一次出现** ——
拿"全文检索 ≤0.98%"当自检，记录自己把自己证明了。三例：`≤0.98%` /
`66600 s` / `M3`+`热供给` 的命中全在版本表或返修记录里，正文一处未改；另有一例是前缀碰撞
（回执要 `q4.moist_max_at_tend`，只加了 `..._minus_60s`，检索照样"通过"）。代价是 review 每轮
重查、每轮打回，白烧几十分钟。

**交 `reports/RECEIPT_LEDGER.json`**：回执里每一条都要交代，且 `applied` 的必须给
probes（一串「改完之后才会出现在正文里」的检索串）：

```json
{
  "schema_version": 1,
  "receipt": "runtime/quality/feedback/<run_id>/<hex>/gate_decision.json",
  "report": "reports/ANALYSIS_MODELING_REPORT.md",
  "items": [
    {"id": "MA-1", "disposition": "applied",
     "probes": ["χ_i = ρ_d(C_i) + C_i·ρ_d'(C_i)", "2|Ṙ|/R 均值/峰值 3.6×10⁻⁵–7.1×10⁻⁵ s⁻¹",
                "min_t[C_s − C_air] > 0", "必修披露清单（6 项）"]},
    {"id": "MA-2", "disposition": "partial",
     "probes": ["≤0.98%"], "remaining": "§9.9 T4 的量级 O(10%) 未写"},
    {"id": "MA-3", "disposition": "not_applied", "reason": "登记表待重排"}
  ]
}
```

四条硬规则：

1. **探针必须在「版本 / 修订 / 返修 / 变更」这类记录节之外命中** —— 记录里那句「已改为 X」不算证据。
2. ASCII 探针按标识符边界匹配 —— `q4.moist_max_at_tend` 不会被 `..._minus_60s` 撞上。
3. 复合判词逐小项给探针：回执的 `fix` 里编了 ①②③④ 的就是 4 个小项，`applied` 要给
   同样多条、互不包含的探针。MA-1 有 4 小项却只给一个探针就签了 `applied` ——
   下一轮门禁把剩下三项原样提出来，白烧一轮。*（分母取 `fix` 不取 `recheck`：后者含"复跑脚本"这类
   验证步骤，拿它当分母会逼你给验证步骤编假探针。）*
4. 没做就写 `not_applied` + `reason`，只做一半写 `partial` + `remaining` —— 诚实登记比谎报便宜
   （review 下一轮照样会查，但那时你要多烧一整轮）。**没做的事不能给探针。**

判据与本检查共用一份代码（`lib/web/receipt_ledger.py`），门禁侧读的是同一份台账，不另写一套。
