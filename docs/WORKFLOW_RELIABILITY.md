# Web 驱动可靠性说明

范围：通用编排、版本回执、交付打包和状态显示（产物目录为两个「最新」指针 + 换题归档 + 各阶段镜像）。历史论文、归档中的求解代码、demo 计算逻辑及模型方法不在本驱动编排的范围内。

## 各项行为与目的

改动这些行为前先运行 `python -m unittest discover -s regression -v`。下表每条行为都有对应回归用例钉住：未裁决放行、旧 APPROVED 覆盖新评审、非零退出被判成功，以及跨问/终验失败和缺报告仍收集交付物，都属于执行路径缺陷，一律按执行路径修，不按外部评分猜测。

| 行为 | 目的 | 验证用例 |
| --- | --- | --- |
| 阶段必须成功退出并生成本次完成标记 | 旧报告不能替代本次执行 | 非零退出、无操作调用、旧文件无回执用例 |
| 裁决 JSON + 严格旧格式兼容 | 不以任意位置的 PASS 字样推断批准 | 否定语句、冲突裁决、过期哈希、JSON/正文冲突用例 |
| 统一静态门禁与人工决策 | 跨问 FAIL、终验 FAIL 必须触发处理动作 | 正常链、建模返修、跨问返修、失败耗尽用例 |
| **失败或超时一律转黄灯等人工决策**（不再自动重试、不再自动回退） | 重试次数耗尽不能改变质量结论 | 持续终验失败只执行三次终验，不执行 demo/收集 |
| 输入和输出哈希回执 | 文件存在不能证明属于本题和本版本 | 无改动续跑、题面变化、报告变化、压缩输入变化用例 |
| 审查阶段只读 | 修改了审核对象便不能沿用原裁决 | 审查中修改对象用例 |
| 生成阶段允许更新派生产物 | 稳健性、绘图等阶段可能合法更新代码/图，不应因此全部误停 | 正常链通过；源题面/数据/plan 在阶段中仍受保护 |
| demo 后如终验对象改变，再次终验 | 后续编辑可能使先前验收失效 | demo 修改论文后出现第二次 verify |
| 暂存失败即停止，归档名唯一 | 避免复制不完整后删除源文件，避免同秒重名 | 路径越界拒绝、两份归档都保留 |
| 先构建新交付包，再归档旧包并切换 | 失败打包不能覆盖成正式交付 | 实际打包成功/缺 PDF 失败与旧包保留用例 |
| 显示挂起、未验证、未完成交付 | “已结束”不能暗示“已通过” | HTTP 状态字段测试；前端脚本语法检查 |

## 运行和首次迁移

入口：`python lib/web/server.py --port 8901`；模型选择、权限模式或看门狗时限不在此处定义。

运行中的服务不会自动加载磁盘上改过的驱动文件；用新驱动前，先结束旧运行再重启服务。

没有可信版本回执时，根目录的 reports/code/results/figures/paper/demo 会被移动到 cache 中唯一命名的归档，再建立新的版本记录；cache 中的历史归档不作为新产物复用。输入变更时产物整包会先按 `cache/<题目标识_日期_时间>/` 归档。此行为避免把旧题的结果默认为新题已完成。request/data/plan 内容变化同样建立新输入版本并归档根目录旧生成物。

同一题目、输入及产物哈希不变且有成功回执时允许复用。单阶段不匹配会使该阶段及其后回执失效；保留实现和章节供修复，但旧完成报告/PDF 会先归档，要求本次重新生成。显式“从某阶段重跑”仍会按原产物清单归档该阶段及后续产物。运行中禁止移动产物或通过 Web 更换题目/数据。

这是保守的顺序依赖方案，不是完整 DAG：例如下游合法修改了上游代码目录，下一次续跑可能从更早阶段重验。宁可多验证，暂不自动认定这种修改无影响。

## 裁决契约

新 Web 提示会提供本阶段的 input_digest，并要求另写 `reports/<报告名>.verdict.json`。审查者原样使用提供的摘要，不改被审查文件；不向建模报告追加 APPROVED。

字段：schema_version=1、stage、input_digest、status、issues。issues 中每项包含 id、severity（hard/soft/info）、evidence、fix、recheck。未解决的 hard/soft 项不能与 PASS/APPROVED/CLEAN 同时出现。可选 target 必须是有效前序阶段。

JSON 缺失时，兼容明确的整题裁决行或独立 PASS/FAIL 等判词。否定句、代码块里的示例、旧建模报告的批准标记不作为批准依据。JSON 存在但无效时，不回退到 Markdown 来绕过错误；JSON 与正文明确判词冲突时标为未验证。

没有必要检查的对象，可以说明“不适用”及依据；有必要检查但未完成，须用 UNVERIFIED。驱动只校验裁决和证据字段，不能证明模型确实完成了目检或数学审核。

audit 的 REVISE_CLAIM 保留为有条件的写作交接；必须存在后续 write，写作收到明确修订要求，后续审查/终验仍要通过。其含义不是计算已被修正。此条件状态不能包含 hard 问题。

## 记录与交付

- `runtime/quality/workspace.json`：输入版本摘要。
- `runtime/quality/stages.json`：最近成功的阶段输入/输出哈希及 run_id。
- `runtime/quality/events.jsonl`：执行、裁决、问题和挂起事件。
- `runtime/quality/feedback/`：返修报告快照，后续修复可以读回原问题。
- `reports/SUBMISSION_MANIFEST.json`：提交清单（同时是论文末页清单表的来源，两边逐项一致）。

提交件在临时目录构建完成后切换进 `<产物根>/提交作品/最新作品/`（切换在这层之内）；
换题时整个「最新作品」被改名成 `<题目标识_日期_时间>/` 归档（「各阶段产物/最新产物」同时改名、
同名）。失败则不标记本轮完成；若切换失败，会尝试恢复旧包。Word 仍为可选导出，
未单独执行版面验收，manifest 明确披露这一点。

磁盘量级（如实记着，别当成异常）：每跑完一题，产物目录大约 **+400 MB** ——
各阶段快照 ≈190 MB（`code/` 108M + `results/` 34M + `paper` / `paper_appendix` 各一份，
其余是报告）、换题时的工作区原件 ≈190 MB、提交包 ≈40 MB。同一题反复重跑因为走增量镜像
（小文件比内容、大文件比 size+mtime），追加量接近 0；换题才会再 +≈190 MB。
要瘦身只有三条杠杆，都要先想清楚代价：① 把 `code/outputs` 从快照里排除（展示区就看不到
数值源头）；② `code`/`results` 只保留最近一次（逻辑复杂化）；③ 换题时那份「工作区原件」
改为可选（它和展示区确有重叠，但覆盖的是阶段的后改动）。

## 测试方式与证据边界

测试基线：456 个 unittest 用例全部通过（约 2.5 分钟；`test_viz_quality` 的编码对账与环境变量无关）；三个 Python 文件的 `py_compile` 通过；前端内联 JavaScript 的 `node --check` 通过。

安装现有 Web 依赖的 Python 环境中运行：

```text
python -m unittest discover -s regression -v
python -m py_compile lib/web/server.py lib/web/workflow_quality.py regression/test_workflow.py
```

测试在独立临时工作区加载真实驱动，替换模型进程调用，使用通用小文件制造成功、失败及修订。HTTP 测试通过 TestClient，不访问现有服务；打包测试不调用 pandoc；测试不运行任何赛题求解或 demo 计算。

通过测试只证明所列控制流和文件行为得到覆盖，不等于验证了真实模型调用、长时间看门狗、整篇论文质量、文献真实性或独立环境数值复现。前端进行了语法检查及 HTTP 数据接口验证，尚未进行浏览器交互验收。

下一篇完整生成仍需检查：JSON 契约遵从率、保守失效带来的重跑开销、目检证据是否充分，以及旧论文中已补规则的问题是否再次出现。
