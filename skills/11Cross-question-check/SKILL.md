# 跨子问题一致性审查

> 一致性核对口径可参考 `../_references/math_modeling_norms.md` 的符号/数据口径相关小节。
> 通用执行纪律（增量返修 / 缩比预估 / 分段落盘 / 方法标记 / 返修只动清单内）见 `../_references/stage_discipline.md`。
> 本阶段适用：一（增量返修，含 1.1 探针复用）、五（返修只动清单内）、六·6.1（先落骨架再深挖）。
> 探针/量测脚本要复用（通用纪律 一·1.1）：本轮写的取证/量测脚本一律留在 `_tmp/`
> （另有散落的在 `tmp/`，两个都要看）；下一轮开工第一步 = `ls _tmp/ tmp/` → 把上一轮
> 为同一批对象写过的脚本先原样重跑（秒级，确认数在当前版本里还成立）→ 只对本轮新出现或改过
> 的对象写新脚本。别每轮从零重写 —— 全链 776 个自写脚本里 **683 个（88%）只被用过一次**
> 就再也没人碰。复用探针 ≠ 跳过复核：探针只是取证手段，判定仍逐条对着当前版本做。


本阶段是完整工作流的第 11 步，位于论文撰写（9Paper-writing）与数学论证门禁（10Math-proof-gate）之后、评分标终审（12Rubric-final）之前。排版（14Layout-and-format）排在内容判据之后：本关与 ⑫ 都在排版之前判内容。排版只动版式、不改内容，所以驱动不会因此把本关拉回来重判 —— 被版式打磨过的内容判官会被标进 `state["layout_superseded"]`（面板上可见），需要时手动重跑该阶段。要害在于：每个子问题局部合理，合在一起可能互相矛盾（符号撞名、数据口径不一、前问结论被后问用错、时点/阈值跨问不一致）。本门禁在论文动笔前做一次全局一致性审查。

## 输入

- `reports/ANALYSIS_MODELING_REPORT.md`（建模与符号）
- `reports/RESULTS_REPORT.md`（各问结果与关键数值）
- `reports/ROBUSTNESS_REPORT.md`（各问稳健性）
- 全局符号表/数据说明（若有单独文件；否则以 ANALYSIS 报告里的符号表为准）

## 必须产出

在当前工作目录的 `reports/` 下创建 `CROSS_QUESTION_REVIEW.md`：

- 逐检查项的结论与证据
- 若 FAIL：明确"哪个子问题 × 哪个符号/口径/结论"需要改、退回哪个阶段（通常是 3analysis 改符号/口径后重跑 5coding/6Robustness 对应问，或仅 9Paper-writing 措辞修正）
- 末尾整题结论：PASS（可进终验）/ FAIL（退回）

Web 裁决侧车（content-quality 启用时）：另写 `reports/CROSS_QUESTION_REVIEW.verdict.json`（v2；本阶段必查 ID 由驱动注入：

> 判词挂在哪个检查项上，决定了它会不会拦链：
> 驱动按 `check_ids` 反推类别（`lib/web/content_quality.py` 的 `RESULT_CHECK_CATEGORY`），
> 而只有纯 `claim` 类判词会走「交给写作、不拦链」那条路（REVISE_CLAIM ⇒ 清单塞进 ⑨ 的提示 +
> 后续终验核查）。所以：
> - 数字/单位/口径/图表与正文不符（能复算证伪）⇒ 挂在 `comparison_validity`（→ validation）
>   或 `task_fidelity`（→ task_interpretation）上 ⇒ 实质类、该拦就拦；
> - 只是表述不自洽/前后措辞矛盾（结论没错）⇒ 挂 `narrative_consistency` + `category: claim`。
> 判词若全挂在 `narrative_consistency` 上 ⇒ 每一轮都会因为措辞级问题把整链停下
> （而驱动里 `severity` 算出来没人读 ⇒ soft 与 hard 一样拦链）。该拦的拦、该放行的放行，靠这一栏分。task_fidelity/comparison_validity/narrative_consistency）。结构、category 路由与锚点要求见 `docs/CONTENT_QUALITY.md`「问题分类与机器裁决」——跨问若暴露题意/模型层不一致（同一约束语义不同、随机过程口径漂移）→ 返修 `analysis`，不能只交给写作措辞。 报告末尾裁决行与 JSON `status` 必须一致；程序校验不通过一律 UNVERIFIED，重试或披露不构成放行。

## 检查项

1. 符号/命名冲突：不同子问题是否出现"同名不同义"或"同义不同名"；符号表中是否统一。全局涉及的概念（如达标阈值、风险分级、关键统计量）各问写法是否一致。
2. 数据与窗口口径一致：各问使用的数据子集、窗口/范围（如时间或空间范围）、缺失处理、单位是否一致；凡数字口径不同（如记录级 vs 个体级）是否在各问都被正确标注且不混淆。
3. 前问结论被后问正确引用：后问是否用对前问的结论/参数（如问题二三的模型基线、问题二与问题三的推荐时点是否互洽）；把前问结论当输入时有没有改口径。
4. 结论自洽：两问如果都在回答相近问题（如都是"最优时点"），结论之间是否矛盾（例如一问说不分组、另一问给了分组，必须有桥接解释；不准静默矛盾）。
5. 数值量级协调：不同问报告的同一指标量级是否一致；可疑跳变要标记。
6. 对"跨问复用结果"做反向抽查：若某问结论强依赖另一问的中间值，独立口算/复核该中间值是否成立。

## 执行方式

1. 先落骨架（§六·6.1）：开工第一步就写 `CROSS_QUESTION_REVIEW.md` 与 `.verdict.json`（`status=UNVERIFIED`、`issues: []`），**不要等查完再写**。子 agent + 复算极容易吃光整段时间；产物留到最后写，一旦跑到没气现场就是一片空白——驱动只报「阶段未成功完成：failed」，读不出任何结论。骨架是占位不是结论，每查完一项必须回填。
2. 通读各 reports，建立全局符号与口径表。
3. 逐检查项核对，记录证据行号。
4. 用 Agent 工具 spawn 一个独立审查子 agent 复核关键项（尤其结论自洽与数值协调）。
5. 汇总定稿 `CROSS_QUESTION_REVIEW.md`。

> **不要自己造重算脚本去验证子 agent 的结论**——那是子 agent 的活，而且它会串行烧掉你在关键路径上的时间（报告只有你能写，你的复算有替代品）。抽查只验子 agent 给出的具体数字，用几分钟内跑得完的短脚本。

### 取证要批量、判词写作要按严重度分档（成本账）

本阶段的成本画像：**207 次 PowerShell/python 调用、82 个写文件、80 次改文件**，
比另一轮（385 次工具调用）多了 46%，整段花了 **41.5 分钟**（同等深度的工作本可 15~23 分钟）。
其中很大一块一次结论都没多出来：

- 每次 `python.exe` 启动 + import fitz/pandas/matplotlib 是 **3~8 秒**。207 次 ⇒ **约 17 分钟纯启动开销**。
- 每条判词各写一个 `.py`、各起一个进程 ⇒ 脚本目录爆炸、进程反复冷启动。

所以：

1. 一个阶段内只写一个批处理探针：`_tmp/cross_probe.py` 吃一份任务清单（要核哪些量、哪些文件），
   一次进程跑完全部机械核验，吐一份 JSON（`_tmp/cross_probe.json`）。报告与侧车里的每一个数
   都从这份 JSON 取 —— 不要一个数一条命令。需要中途加一条核验 ⇒ 改那个脚本再跑一次，
   不要新开一个 `.py`。（这与通用纪律 一·1.1 的"探针要复用"是同一件事，只是同阶段内也要复用。）
2. 纯读文件就能拿到的数（`results/*.json`、`reports/*.json`、`figures/manifest.json`、
   `pdftotext` 的文本层）一律直接读，不为它起进程。
3. 判词写作按严重度分档：
   - `hard`（会拦链、要回退上游）：写完整证伪链 —— 多路证据、给读数、给反解；
   - `soft` 与 `advisories`（不拦链）：只写一条最直接的证据（`文件:行` + 读数）与打算怎么改。
     侧车不是论文，堆字数不增信，只增生成时间。
4. 报告与侧车边查边回填（§六·6.1），但回填的是结论，不是草稿的反复重写 —— 改文件次数
   计入上面的成本账：80 次里有一部分是同一段话改三遍。

## 门禁动作

- PASS：标记后可进入 15Verification。终验可引用本报告说明"全局一致，已核对"。
- FAIL：给修改清单退回对应子问题修复；修复后复跑本审查。

## 阶段边界

- 不重新建模、不重跑大规模实验；只做一致性与自洽性核对。
- 发现需要改模型/改口径的真问题时，退回对应阶段并写明，而不是在论文里粉饰。

### 动态交回规则（跨问审查发现真矛盾要修时）
本审查若发现"必须改某问的建模/代码/数据口径才能消除的矛盾"，除写 PASS/FAIL 报告外，创建 `reports/HANDBACK_REQUEST.md`：
```
target: <analysis | code | robustness | audit>   # 该矛盾需回退到哪个生产阶段修
reason: <哪问 × 什么矛盾，期望改法>
```
编排器会把它作为回退建议交给用户决策；确认后补跑，再重跑本审查。仅当矛盾属"论文措辞即可弥合"时不触发。
