# 数据与结果可信度审计

> 审计清单见 `../_references/math_modeling_norms.md` 末尾「C. 数据严谨性 / 结果可信度」。
> 通用执行纪律（增量返修 / 缩比预估 / 分段落盘 / 方法标记 / 返修只动清单内）见 `../_references/stage_discipline.md`。
> 本阶段适用：一（增量返修，含 1.1 探针复用）、五（返修只动清单内）、六·6.1（先落骨架再深挖）。
> 探针/量测脚本要复用（通用纪律 一·1.1）：本轮写的取证/量测脚本一律留在 `_tmp/`
> （另有散落的在 `tmp/`，两个都要看）；下一轮开工第一步 = `ls _tmp/ tmp/` → 把上一轮
> 为同一批对象写过的脚本先原样重跑（秒级，确认数在当前版本里还成立）→ 只对本轮新出现或改过
> 的对象写新脚本。别每轮从零重写 —— 全链 776 个自写脚本里 **683 个（88%）只被用过一次**
> 就再也没人碰。复用探针 ≠ 跳过复核：探针只是取证手段，判定仍逐条对着当前版本做。


本阶段是完整工作流的第 5 步，位于编码（5coding）之后、稳健性（6Robustness）之前。它只做一件事：判定"这份数据的结论可不可信"——针对自动建模工具在"数据不严谨"上的已知弱点（例如：小样本上宣称 AUC≈0.98、记录级与个体级口径混用、训练/测试泄漏、标签口径错位）做专项审计。

设计原则（与全工作流一致）：本 skill 职责单一，不掺入建模/稳健性/写作，避免上下文过载导致审查变浅。若感觉需要同时盯多个审查维度，用 Agent 工具把它们拆给不同子 agent。

## 结构化数值与独立校验

本阶段：`python -m lib.result_contract audit`（只读审计，不补写被审结果）；细节见 docs/RESULT_CONTRACT.md。

## 输入

- `reports/RESULTS_REPORT.md`（5coding 结果）
- 5coding 的代码目录 `code/` 与结果文件
- 3analysis 报告中的数据口径说明

> 本阶段排在 6Robustness 之前，所以 不读 `ROBUSTNESS_REPORT.md` —— 那时它还不存在。
> 换序的理由是成本：本阶段基本只读 + 小脚本复核（便宜），6Robustness 要跑 bootstrap/扰动（贵）。
> 本阶段要审的是「这份结果可不可信」（泄漏/分析单位/样本量/标签口径）——结果不可信时，
> 在它上面做的一切扰动全是白做。便宜的先跑，把废品挡在贵阶段之前。

## 必须产出

在当前工作目录的 `reports/` 下创建 `RESULT_AUDIT_REPORT.md`：

- 逐项审计结论（每项 PASS / 需修正 / 不可信，附证据：哪个文件/哪段代码/哪个数）
- 若判"需修正/不可信"：给出具体修法（改划分、改口径、降级表述、补 PR-AUC 等）
- 末尾整题结论：CLEAN（可信，放行到 6Robustness —— 本阶段排在它之前）/ NEEDS_FIX（退回 5coding 修正后重跑 code，再跑本审计）

> 什么时候用 `REVISE_CLAIM`：模型、实现、验证都没错，只是报告里的结论话说满了
> （小样本上称「高精度」、best-known 称「全局最优」、区间估计当点估计报）。
> 这时**必须挂在 `claim_scope` 这个检查项上**并填 `category: "claim"`：
> 它是本阶段唯一不在 `RESULT_CHECK_CATEGORY` 反推表里的必查项，只有它能发出 claim 类 issue。
> 其余 7 个必查项全部在反推表里 —— 无论你填什么 category 都会被按检查项掰回
> `analysis`/`code`，于是「只是措辞」的判定会变成回退重算（小时级），那不是你要的。
> 判定顺序：先问「算错了没有」——错了就是模型/实现问题，正常判 NEEDS_FIX；
> 确实没错、只是表述超出证据，才是 `claim_scope` + `claim`。

Web 裁决侧车（content-quality 启用时）：另写 `reports/RESULT_AUDIT_REPORT.verdict.json`（v2；本阶段必查 ID 由驱动注入：task_fidelity/quantifiers/stochastic_semantics/implementation_fidelity/feasibility/optimality/comparison_validity）。结构、category 路由与锚点要求见 `docs/CONTENT_QUALITY.md`「问题分类与机器裁决」——**模型层错误（约束语义/随机过程/题意映射）必须返修 analysis/code，不得靠改措辞或写进局限放行**；只有模型与实现都对、仅剩纯措辞过强时才可 REVISE_CLAIM 交写作。 报告末尾裁决行与 JSON `status` 必须一致；程序校验不通过一律 UNVERIFIED，重试或披露不构成放行。

## 返修收敛纪律（必读）

- 边际改进门槛：若被审方案的最优性等级是 best-known/启发式，且**已知残余可行增益 < 1e-3 s 或 < 0.01%**，
  只在报告里核对"是否如实披露了该残余"——披露了就 PASS；**不得**以"被支配/非局部最优"判 FAIL/NEEDS_FIX，
  也不得要求退回重优化（对连续/黑箱问题残余为零不可达）。判据是证据与措辞自洽，不是残余为零。
- 报告一致性缺陷的 category：同一数字多处不一致、口径标注矛盾、表与正文不符、pp/区间前后不一 →
  category 只能填 `claim`/`presentation`（→write）或 `validation`/`implementation`（→code）。
  **禁止**填 `task_interpretation`/`constraint_model`/`stochastic_model`——那会把整链拽回建模设计（小时级代价）。

## 审计项（每一项都要过）

1. 指标异常乐观审查：判别类问题，报告性能 vs 样本量与阳性数是否合理。经验校准：阳性数很少（如 <50）时 AUC/准确率 >0.95 必须主动怀疑；并要求核对是否同时报了 PR-AUC（类别不平衡下 ROC-AUC 会虚高）、灵敏度/特异度是否与混淆矩阵自洽。
2. 泄漏回查：训练/测试是否按个体/孕妇分层；特征是否混入"结果/事后"变量（即把本应预测的最终结果/事后标签当成了输入特征）；归一化/填补/特征选择是否只在训练折上做。查代码确认，不只查报告措辞。
3. 分析单位复核：性能是按"记录"还是按"个体"算？有没有把记录级数字当个体级结论（或反之）？每个用到数字的结论都要能说出单位。标记不一致并给正确口径。
4. 小样本稳定性：阳性极少的分组/类别，波动范围多大（留一或小 bootstrap）；波动过大要求降级为"仅描述/需更多样本"，禁止确定结论。
5. 标签口径：用哪个标签、报告是否一致；多标签（若存在两个口径不同的结果标签）差异是否处理并披露；结论对标签选择是否敏感。
6. 可复现性抽查：结果能否由 code/ 复现（seed 是否固定、随机状态是否记录）；若报告的数字代码里找不到来源，标记。

## 执行方式

1. 先落骨架（§六·6.1）：开工第一步就写 `RESULT_AUDIT_REPORT.md` 与 `.verdict.json`（`status=UNVERIFIED`、`issues: []`），**不要等审完再写**。复算脚本极容易吃光整段时间；产物留到最后写，一旦跑到没气现场就是一片空白——驱动只报「阶段未成功完成：failed」，读不出任何结论。骨架是占位不是结论，每审完一项必须回填。
2. 按审计项逐项读报告 + 查对应代码/结果文件核对（不只看报告措辞）。
3. 对可疑点做小脚本复核（如重新分层 CV、算 PR-AUC、查特征列）——审计要落到代码与数字，不是感觉。脚本要几分钟内跑得完：本阶段是门禁，唯一无可替代的产物是报告，复算有替代品（审不动就如实写"待核实"，别把时间全烧在自己的脚本上）。
4. 汇总定稿 `RESULT_AUDIT_REPORT.md`。

## 门禁动作

- CLEAN：放行到 6Robustness（本阶段排在它之前，中间不隔别的阶段）。
- NEEDS_FIX：把审计证据与修法退回 5coding 修正、重跑 code，再跑本审计。本阶段只跑一次：这一轮仍不过就转黄灯由用户决定。
- REVISE_CLAIM：结论必须降级/如实表述才能进写作（在报告写明应如何表述）。

## 阶段边界

- 不重新建模、不重新做完整稳健性（那属于 3analysis/6Robustness）。
- 只审计"数据与结果是否可信、是否如实表述"，不替 3Modeling-review-gate 审建模方案。
