# 交互式系统开发（16Web-demo）

> 通用执行纪律（增量返修 / 缩比预估 / 分段落盘 / 方法标记 / 返修只动清单内）见 `../_references/stage_discipline.md`。
> 本阶段适用：一（增量返修，含 1.1 探针复用）。
> 探针/量测脚本要复用（通用纪律 一·1.1）：本轮写的取证/量测脚本一律留在 `_tmp/`
> （另有散落的在 `tmp/`，两个都要看）；下一轮开工第一步 = `ls _tmp/ tmp/` → 把上一轮
> 为同一批对象写过的脚本先原样重跑（秒级，确认数在当前版本里还成立）→ 只对本轮新出现或改过
> 的对象写新脚本。别每轮从零重写 —— 全链 776 个自写脚本里 **683 个（88%）只被用过一次**
> 就再也没人碰。复用探针 ≠ 跳过复核：探针只是取证手段，判定仍逐条对着当前版本做。

把建模结果做成一个真正能跑、参数可调、结果实时更新的单页 Web 工具。不是静态展示页、不是"为了截图拼的界面"——是评委/用户打开就能用的交互式系统。

## 定位与边界

- 本 skill 负责：交互式系统的功能逻辑 + 真实数据 + 交互流畅 + 结构清晰的 UI。
- 本 skill 不负责：UI 视觉美化（配色/动效/排版精修留给用户后期设计）；不产生"新的分析/新的数值"——系统里的每个数都能溯源到 `reports/RESULTS_REPORT.md` 或 `code/outputs/*.json`。
- 已接入正式链：作为 verify（验收、PDF 定稿）之后的末段阶段运行——PDF 先产好、用户可随时打开，web demo 在不影响论文的前提下补充交互落地。凡题含"条件/参数→结果"式可执行结论（推荐/决策/优化/预测/判定/评价类）都应产出；纯机理推导/纯证明/无可交互参数的题则跳过并在 `DEMO_REPORT.md` 说明原因。

## 触发条件（什么题适合做）

适合：有"条件/参数 → 建议/结果"式可执行结论的子问题。典型：

- 推荐/分组类：选 BMI 区间 → 显示推荐时点
- 决策类：选参数 → 显示最优方案/分组
- 判定类：输入指标值 → 显示三态判定/转介
- 预测类：调参数 → 实时重算预测曲线
- 优化类：改约束/权重 → 显示最优解变化

不适合（做了也白做）：纯机理推导、纯证明题、没有可交互参数的题。若题不适合，说明原因并建议不做。

## 三条纪律

1. 功能优先：参数真的能改、结果真的实时重算、交互流畅（无卡顿/无假结果）。不是静态展示。
   - **图表必须响应输入**：任何与输入参数有关的图（折线/柱状/曲线），都必须在输入变化时实时更新，并带当前状态指示——如"当前 q 位置的竖线/高亮点"、"当前选中项高亮加粗（其余变淡）"、"游标标记当前取值"。**禁止画一张静态图**让用户调了参数图却纹丝不动——那是假交互。
2. 数据真实：系统里每个数值、每条曲线都来自 RESULTS_REPORT 或 outputs，可溯源；DEMO_REPORT 里写清数据来源。**禁止**前端"编一个看起来对的数"。
3. UI 留白但结构清晰：不花时间做精美视觉；但 DOM 语义化（`<select>`/`<input type=range>`/结果区有 id）、CSS 用变量（`--primary` 等）集中定义，让用户后期改主题只需动一处。结构要让"换皮"很容易。

## 计算架构决策（关键：决定"流畅"与"真实"）

先判断目标结论的计算复杂度，二选一：

A. 前端重算（公式简单时优先）：插值、查表、线性/多项式、简单 logistic/指数、闭式解——用 JS 在前端直接算。最流畅、单文件、离线可用。

B. 预计算查表（公式复杂时）：需要 python 拟合/优化/数值积分/枚举才出的结果——用 python 预计算一组参数网格 → 结果，存成内联进 `demo.html` 的 JS 数据块，前端查表 + 线性插值。要保证网格够密、插值误差可忽略，并在 DEMO_REPORT 里说明插值方法。

**绝不做**：为了"看起来能算"而让前端显示与真实模型无关的假公式。若某参数无法在前端真实重算，就改为"预计算查表"，或明确标注"该参数为演示档位，非连续可调"。

## 产出物

```
demo/
  demo.html       # 单文件，就是提交件本身：JS/CSS/数据全部内联
  shot_*.png      # 截图存档（交付要求，见工作流第 5 步）
reports/DEMO_REPORT.md   # 功能说明 + 数据来源清单 + 交互说明 + 待用户后期美化的点
```

本阶段还动一处别处的产物（唯一的一处）：把首屏截图安进附录的
第一页（`paper_appendix/sections/A_appendix.tex` 插一行 + `paper_appendix/figures/demo_shot.*`
+ 重编 `附录A.pdf`），做法见工作流第 6 步。**正文 `paper/` 一个字都不许动。**

**产出的就是 `demo/demo.html` 这一个文件 —— 不要拆成 `index.html` + `app.js` + `data.js` +
`style.css`。** 提交件里它独立存在、名字就叫 `demo.html`，双击即用、离线可用，所以：

- CSS 写在 `<style>` 里，JS 写在 `<script>` 里，数据直接内联成 JS 字面量/JSON
- **不得**出现任何指向本地文件的引用：`<script src="app.js">`、`<link href="style.css">`、
  `<img src="data/x.png">` 一律不行 —— 提交件里没有那些文件，页面会白屏
- 需要图表库时把整个库内联进 `<script>`（或优先用内联 SVG/Canvas 自绘）；
  不许 `<script src="vendor/chart.js">`，也不许联网 CDN（比赛现场可能没网）

> 「多文件开发 + 打包时合并」这条路走不通：`vendor/` 里的库合并不进去，
> 交付后照样打不开。从源头就产单文件最省事。
> `delivery` 会机械校验这一点：`demo/demo.html` 里出现本地引用就直接报错。

图表：优先内联 SVG/Canvas 自绘（不依赖联网 CDN，离线也能跑）；确实要用 Chart.js 之类的库，把库整个内联进 `<script>`，不靠 CDN、也不留 `vendor/`。

## 工作流

1. 读结论与数据：读 `reports/RESULTS_REPORT.md` 对应子问题 + `code/outputs/*.json`，确定"哪些是输入参数、哪些是输出结论、输出怎么随输入变"。
2. 定计算架构：按上面 A/B 二选一；复杂公式用 python 预计算网格，写清插值。
3. 写 demo/：一个 `demo/demo.html` 写完 —— 数据块、逻辑、样式、结构都在里面（想清楚再写，别先生成一堆文件再合并）。
4. 自测：本地用浏览器打开 `demo/demo.html`，逐项验证——每个输入改动都触发正确结果更新、无 console 报错、数值与 outputs 一致。必查项：① 拖动/修改每个输入，对应的数字结果是否实时变；② 每张与输入有关的图是否随输入更新并带当前状态指示（竖线/高亮点/高亮当前项），不是静态图；③ 有没有任何"输入改了、页面某处却纹丝不动"的死角。
5. 截图存档（交付要求，不是可选）：用 headless 浏览器给 demo 截图，存进 `demo/`，并在 `DEMO_REPORT.md` 里列出每张截图对应的状态。
   - 至少 **3 张**：①首屏默认状态；②拖到某个有代表性的非默认输入后的状态（要能看出数值/图随输入变了）；③（若有多个子问题/视图）切换/展开后的状态。
   - 命令（无需装 Playwright；先把 `demo/demo.html` 的绝对路径求出来再拼 `file://` URL，
     别在提示里留 `<绝对路径>` 这样的占位符直接抄）：
     - Windows：`msedge --headless=new --disable-gpu --window-size=1400,900 --screenshot=demo/shot_default.png "file:///<abs>/demo/demo.html"`
       （Edge 不在 PATH 时用 `"C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"`）
     - Linux：`chromium --headless=new --disable-gpu --window-size=1400,900 --screenshot=demo/shot_default.png "file:///<abs>/demo/demo.html"`
       （或 `google-chrome`；容器里加 `--no-sandbox`）
     - macOS：`"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new …`
     - 真一个浏览器都没有时：写一份 `demo/自测记录.md` 说明"没有可用的 headless 浏览器"，
     并把①的判据改成人工清单（列出你逐个改过哪些输入、预期什么变化），**不要**用
     `DEMO_REPORT.md` 里一句"已截图"糊过去 —— 没有截图就等于这一条没做。
   - **截图必须能看出交互生效**（图上带当前输入值/高亮点），不能是两张看起来一样的图。
   - 这些截图是交付物的一部分（随 `demo/` 进产物的 `其余文件/`），供用户放进论文或答辩材料。
6. 把 demo 整段安进 `附录A.pdf` 的最前面（标题 + 图 A1 + 一段介绍） ——
   参考件 `C:\Users\Cyl\Desktop\最终拆分\其余文件\附录\main.pdf` 的第 1 页就是：

   ```
   demo 交互式网页与工程实现展示         ← 与 A.x 同级的小节标题（参考件同为 14.9pt 粗体）
   图A1：药材烘干交互式网页截图
   页面把论文的建模链路（统一建模内核→结构命题→逐问求解→结果核验）整条做成了可交互的形态：……
   工程可用性：交付件为单个约 0.8 MB 的离线 HTML 文件，无 CDN、无外部请求……
   A.1  问题一、二的误差与守恒汇总          ← 原有小节完整地跟在后面
   ```
   标题不带括号：参考件原样是「（展示）」，**不要照抄参考件**。

   ① 先写介绍：把 demo 的说明写进 `_tmp/demo_intro.tex`（纯文本、UTF-8）。照参考件的路子，
      分几个自然段讲清四件事 —— 这是什么（一句话）、方法贯通可视化（把论文的链路做成了
      哪几个页面/视图）、稳健性与负对照（哪些页是拿来证伪的）、工程可用性（文件多大、
      离线双击即用、深链、配套多少项回归）。**每一条都要对得上你自己的 `demo.html` 与
      `DEMO_REPORT.md`**：页数、视图数、文件大小、回归项数一律用你自己数出来的实际值，别照抄参考件的数字。
      长度 **400–800 字**为宜（参考件约 600 字）。**不要数学公式、不要 `%`**（脚本会把裸 `%` 转义，
      但你干脆别写更省事）。
   ② 再一条命令安进去：
   ```bash
   python lib/web/appendix_demo_figure.py --png demo/shot_1_default.png --intro _tmp/demo_intro.tex
   cd paper_appendix && xelatex -interaction=nonstopmode main.tex && xelatex -interaction=nonstopmode main.tex
   ```
   - **不要自己去改 `A_appendix.tex`**。附录的图号是手打的纯文本（`\appfigure` 用 `\caption*`，
     不产生编号），在最前面插一张新图要把后面 7 张连同 6 处行文按号指路一起顺延；而且这几段要
     整段可替换 —— 脚本按注释界标整段摘除再插入，幂等（本阶段重跑不会插出第二段）。
   - 标题、图题、编号都由脚本写死：`demo 交互式网页与工程实现展示` / `图 A1：交互式网页首屏`。
     `--intro` 为空的会被脚本拒绝（只放一张光图不算数）。
   - 位置是「所有 A.x 小节之前」，不是"A.1 标题之后"。插在 A.1 标题与它的正文之间会
     把 A.1 劈成两半。参考件里 demo 是自成一段打头、A.1 完整跟在后面。
   - 编译完目检第一页：demo 标题 → 图 A1（整栏）→ 介绍；翻到 A.1 时，它的标题下面紧跟着
     就是它自己的正文，中间没有图。原来那批图顺延成 A2…A8，无重号无跳号。`xelatex` 跑两遍。
   - 为什么这一步由本阶段做、而不是回退到 ⑭：⑯ 排在 ⑭⑮ 之后，而这张图只有本阶段才产得出来。
     `附录A.pdf` 没有哈希绑定（`lib/publication/checks.py` 只绑 `paper/main.pdf`），重编它不
     破坏任何绑定；本阶段收尾时驱动会自动重打包交付件，提交包里那份 `附录A.pdf` 会跟着更新。
   - **正文一个字都不许动** —— 正文已经写满 30 页额度（摘要 1 + 正文 29），本阶段只进附录。
7. 写 DEMO_REPORT：列出每个交互项对应的数据来源、计算方式（重算 or 查表+插值）、截图清单、以及"建议用户后期美化/增强的点"（如配色、响应式、移动端适配）。
