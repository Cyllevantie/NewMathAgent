# 赛题分析与建模设计

> 通用执行纪律（增量返修 / 缩比预估 / 分段落盘 / 方法标记 / 返修只动清单内）见 `../_references/stage_discipline.md`。
> 本阶段适用：一（增量返修，含 1.1 探针复用）、五（返修只动清单内）、六·6.2（收尾自检题意契约）、**六·6.3（返修台账不许自证）**。
> 探针/量测脚本要复用（通用纪律 一·1.1）：本轮写的取证/量测脚本一律留在 `_tmp/`
> （另有散落的在 `tmp/`，两个都要看）；下一轮开工第一步 = `ls _tmp/ tmp/` → 把上一轮
> 为同一批对象写过的脚本先原样重跑（秒级，确认数在当前版本里还成立）→ 只对本轮新出现或改过
> 的对象写新脚本。别每轮从零重写 —— 全链 776 个自写脚本里 **683 个（88%）只被用过一次**
> 就再也没人碰。复用探针 ≠ 跳过复核：探针只是取证手段，判定仍逐条对着当前版本做。

> **创新第一原则：主答案优先。** 任何创新默认只能让主答案在 `primary_guard` 内变化；
> 主答案大幅偏离基线（例如温度 33 ℃ → 5 ℃、空气 41 ℃）又拿不出独立证据，先按模型没闭合
> 处理，不是“方法更精细”。先保住简洁模型的答案，再谈改进；复杂模型不能单独覆盖主结果。

- `reports/INNOVATION_LEDGER.json`（本阶段必写的**设计台账**；③ 只读它。
  ④⑥⑨ 分别写 `INNOVATION_MEASUREMENT.json` / `INNOVATION_ROBUSTNESS.json` /
  `INNOVATION_PAPER.json`，**不得回写设计台账**）：
  - 记全部候选（含 rejected），不是只记采用项；至少 3 条，`panel.lenses` 至少 4 个不同视角，
    且 `closure` 与 `adversarial` 各至少要有一个（纯优化/决策题可用 `optimization` 顶替其中
    一项；不能两项都靠同一个 optimization 顶替，否则凑不满 4 个不同视角）。另两条从
    mechanism/data 里取。
  - `kind="innovation"` 的 adopted 最多 2 条（1 core + 1 supporting），每条必须有
    `core（true/false）/ baseline_id / failure_mode / intervention / claim / predicted_delta /
    test / kill_if / primary_guard`；全篇最多 1 个 `core=true`。
  - `primary_guard` 只属于 innovation，写主答案是什么、允许相对变化多少（默认 10%）、为什么；
    主答案超出护栏且无独立证据 → 不能 adopted。
  - `kind="contribution"` 的 adopted 最多 3 条、`core` 必须 false；必须有
    `contribution / baseline_is_naive / contribution_evidence`，不要求 `primary_guard`。
  - 没有 adopted 时写 `no_adoption_reason`（为什么本题没有值得做的增量），不许空着；
    但 ⑨ 仍会因 2.5 为空打回 ②（见 Step 3.7）。
  - 收尾自检：`python lib/web/check_innovation.py --stage design`。
- `reports/TASK_CONTRACT.json`（启用 content-quality 时必写：项目根存在 `docs/CONTENT_QUALITY.md` / `config/content_quality.json`；schema 见前者「题意契约」）：
  - 把题面每条硬条件与交付要求映射为一个 requirement：`{id, source:{file,quote}, source_semantics, model_semantics, model_anchor:{file,quote}, status:"mapped"}`。
  - `source.quote` 必须是 `request/` 下文件（题面/附件说明）中逐字存在的原文（子串匹配，照抄含标点，别改简繁/空格）；`model_anchor.quote` 指向本报告里对应模型定义的原文。
  - `source_semantics`/`model_semantics` 各含 `quantifier/scope/unit/time_reference`，如实写"题面语义"与"你模型实际语义"并保证一致；程序只查两端一致，评审会独立对照原文，不许两端一起填错蒙混。
  - **禁止弱化**：题面"所有子单元/覆盖全部面积"不得写成"至少一个/发生过一次"；累计面积不等价于空间覆盖。随机量写清基期、是水平还是增量、是否逐年累积、跨期依赖（例：题面"每年相对 2023 约 ±5%"是固定基期波动，不是上一年连乘）。
  - status 填 `mapped` 的项其锚点必须真实有效；变化时更新锚点，不得保留失效原文引用。

### 任务覆盖与证据边界

逐项回答题面明确要求，并区分“有数据支持的结果”“附带假设的情景方案”“当前无法识别的量”。不得为了凑交付粒度编造阈值、强行分组或夸大统计证据。

- 题面明确指定的格式和交付粒度须覆盖；缺数据或缺模板时记录缺口、影响与可完成的部分，不把自制文件冒充指定模板。
- 证据不足时，说明原因；能够给出条件方案时明确假设、适用范围和验证限制。确实不可识别时允许报告不可识别及需要补充的数据，不能给无依据的确定结论。
- 简单模型、不分组、负结果或边界解不自动视为失败。与适当基线比较，核对题面约束和实现；符合题意且证据支持就保留。
- 对未覆盖的题面要求给出具体原因和补救方式，评审区分“遗漏/未尝试”和“经分析确有证据限制”。

不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。


## 工作流程


### Step 0（前置）：题面硬约束与交付契约清单

动手拆题前，先在 `ANALYSIS_MODELING_REPORT.md` 开头写一小节”题面硬约束与交付契约”，逐条列出**任何模型都不得违反**的边界 + **必须交付**的东西，建模全程以此为锚、防漂移：

- 硬约束（候选不得破坏）：题面给定的物理定律/几何关系/数值常量（如速度范围、间隔下限、尺寸/半径）、数据给定条件、格式/单位要求、可行性要求。
- 不可违反项：不允许通过绕过题意、忽略数据、改口径来”做出来”。
- 交付边界：本题要求交什么（如特定模板/表/文件、指定格式的数值），哪些研究材料留内部不进论文。
- 附一行”为什么”给每类约束（为什么它是硬的、违了会怎样），供评审核对。

每个子问题建模时都对照本清单自查：模型/解是否仍满足硬约束、是否覆盖了交付项。发现题面某处理解有歧义、需放宽某约束时，在假设预检里显式记录并给依据，而不是悄悄忽略。

### Step 1: 子问题拆解

只把题面中明确编号的顶层问题当作子问题，例如”问题一/二/三””Problem 1/2/3”。不要把小问、背景描述、数据说明、提交要求误当成独立子问题。

在 `ANALYSIS_MODELING_REPORT.md` 开头明确写：

根据题目动态调整问题数量

本赛题共 X 个子问题。

每个子问题要说明：

- 输入数据和已知条件。
- 决策变量或预测对象。
- 目标函数或评价指标。
- 约束条件。
- 与其它子问题的依赖关系。
- 绘制哪些图像或表格来展示结果。

### Step 2: 假设敏感性预检

列出关键歧义，不要急着定模型。对影响结果的歧义至少给出两种解释，并用简单验算或逻辑递进判断选择。

必须在 `ANALYSIS_MODELING_REPORT.md` 中包含：

```markdown
## 假设敏感性预检

### 模糊表述及解释
...

### 快速验算与递进性检查
...

### 最终采用的解释
...

### 绘制的图像和对比表格


```

如果某个假设会让后续问题的新增条件没有边际效果，要回头调整解释.

可行域截断审计（防"自设假设卡掉更好解而不自知"）：凡是缩小了可行域/解空间的建模假设或决策（τ 下界、整机指派/一机只服务一目标、每机≤N 弹、固定航路/走廊、离散格点、忽略可穿插/可拆分等），必须在建模报告里给它单独一行"截断审计"：①明确写出它排除了哪些本可存在的策略族；②预期代价 + 复算/复核计划（在哪一步做"去掉该假设的粗重优"并报告 Δ）；③若该假设纯为求解便利（非题意/非物理硬约束），必须标注并在 6Robustness 兑现松弛审计。**不许**把"工程简化"当"题面约束"写，也**不许**只披露不审计。优化题的最终结论须能说清"在全空间/在假设结构内"：只有假设结构内的，才称结构内最优；全空间结论要有相应审计支撑或明说未覆盖。

### Step 3: 数据理解与建模路线

对每份附件做数据理解：

- 行列规模和字段解释。
- 缺失、异常、重复、单位不一致。
- 可直接用于建模的变量。
- 需要派生的指标。

然后给出总体路线：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> 。。。。 -> 结果检验 -> 论文展示
```

### Step 3.4: 基线卡（先写基线，再谈创新）

创新不是“用了什么方法”，而是“基线在什么条件下会错，我们改了什么，改完哪个数字变了”。
每问先写一张基线卡，写进 `ANALYSIS_MODELING_REPORT.md` 的「创新点与取舍」小节：

| 问 | 基线模型（最简可辩护） | 头条数字/决策 | 单位 | 已知失败模式 |
|---|---|---|---|---|
| Q1 | 一维径向有限体积 + 题给物性 | 1800 s 末含水率 | kg/kg | 表面活度取 Ce=Y 可能高估干燥速率 |
| Q4 | 材料坐标 + 实测 R(t) | 达标时间 t_dry | h | R(t) 只作输入，收缩与失水关系未被检验 |

硬要求：

- 基线必须是**本题最简、可跑、可辩护**的方案，不是“随便一个能出数的模型”；
- 头条数字/决策必须是论文要回答的那一个（如 t_dry、最大含水率、成本、分组数）；
- 失败模式要具体到方程/边界/数据口径/判据/决策，不写“精度不够”“效果一般”；
- `kind=contribution` 的朴素基线如果与该问主基线不同，另写一张基线卡（如 `BASE-Q4-N`），
  并在台账里让 `baseline_id` 指向它；不要拿主模型当朴素基线。

**输入过定 / 闭合检查（开面板前必做）**：列出“同一物理量/几何被多个输入重复定义”的地方。
典型：题给 R(t) 与附录的 ρ_b(C) 同时定义干物质存量；两者不能同时当独立物理输入。若存在过定：

- 基线卡必须写“**主闭合是什么、哪个量只作诊断**”（例如 ρ_s∝R⁻² + 固体连续性；ρ_b(C) 只进热容；
  干物质审计是输入过定诊断，不是数值质量泄漏）；
- 创新面板必须至少提一条 `type=closure` 候选（见 Step 3.6 D），并且它必须有一个**朴素基线**
  （不采用该闭合时的错误/不完整模型）与一致性/差值证据。

**主答案护栏（最重要，仅 `kind=innovation`）**：每个 innovation adopted 项另写

```json
"primary_guard": {
  "metric": "1800 s 中心温度",
  "allowed_relative_change": 0.10,
  "why": "题给空气温度 41.5 ℃ 与多数模型的量级；超过 10% 必须有独立证据"
}
```

创新默认只能让主答案在护栏内变化；如果主答案大幅偏离基线（例如温度从 33 ℃ 掉到 5 ℃，
而空气是 41 ℃），先按**模型没闭合**处理，不叫创新。必须有独立证据（实验/文献/题面给定值/
多模型一致/解析极限）证明是基线错了，否则只能降级为负结果/局限。innovation 没有护栏，
不许 adopted；`kind=contribution` 不写护栏，改用“朴素基线 + 证据”的门槛（见 Step 3.7）。

**创新的形态**：优先“简单模型 + 一个可控增量”（加一项闭合、换一个判据、证明一个结构），
而不是“换一套模型把主答案带走”。如果确实要换模型类，baseline 与 intervention 都保留：
主结果先按基线报，创新只作为条件性改进；除非独立证据表明基线错，否则不要让复杂模型
覆盖主答案。这样评委看到的是“在原答案上改进”，不是“算出了另一个世界”。

**温度/能量类尤其**：加潜热/相变/辐射前，先做能量收支与边界量级检查；如果加完后温度
低于环境温度、又没有表面蒸发冷却/活度闭合解释，按模型错误处理，不要写成“更精细的模型”。
同理，浓度/压力/成本类创新先做守恒与边界检查，再看主答案有没有越过护栏。

没有基线卡，不许开创新面板。

### Step 3.5: 创新分级（先认清什么算创新）

| 级别 | 定义 | 竞赛里怎么算 | 例子 |
|---|---|---|---|
| L0 | 正确实现标准方法 | 不算；但必须有 | 有限体积、Brent、PSO |
| L1 | 标准方法适配本题 | 弱；只能叫“关键处理” | 材料坐标处理收缩 |
| L2 | 任务特定的结构观察/判据 | 可算创新，但必须有可测 delta | 单调性 → 一次求根 |
| L3 | 新机制/新状态/新决策链，改变结论 | 强创新；目标 | 收缩作为状态、风险冗余 |
| L4 | 新通用方法 | 罕见；不要求 | — |

判据四因子：

```
创新 = 反常识洞察 × 可证伪机制 × 可测量改变 × 任务相关性
```

- **反常识洞察**：题面/文献没有直接给出，需要推导或对照才能看见；
- **可证伪机制**：能写出“若……则……”，并有一个可能失败的 test；
- **可测量改变**：对头条数字/决策给出方向与量级，或定性翻转；
- **任务相关性**：改变的是题目要回答的东西，不是顺手多算一个指标。

以下**本身不算创新**：用了有限体积/PSO/机器学习；考虑了收缩/端面/变物性；做了灵敏度分析/
网格收敛；精度更高；把三个模型拼在一起。它们没有朴素基线 + 一致性/差值证据时只是
L0/L1 或验证工作；补上“朴素基线 → 本文处理 → 证据”后可作为 `kind=contribution`
（模型特点与关键处理），但仍不能叫核心创新。

**两类正面内容（论文 2.5 不能为空）**：

- `kind="innovation"`：基线是**主模型**，干预是增量，比较可测 delta 并守住主答案护栏；写“本文主要创新点”。
- `kind="contribution"`：基线是**朴素/不完整模型**（例如固定域、体积平均判据、把 R(t) 与 ρ(C)
  同时当独立输入），本文做法是任务特定的**闭合/结构/判据**；用一致性、必要性或差值证明，
  不要求推动主答案。写“模型特点与关键处理”。

两类项都有时，2.5 标题写「本文主要创新点与模型特点」：创新点用 `\textbf{创新点X：}`，
贡献用 `\textbf{关键处理X：}`，两类都逐条写“基线 → 本文处理 → 证据/差值”。

contribution 不是“没创新”，而是论文的模型贡献：例如“自洽收缩闭合（ρ_s∝R⁻² + 固体连续性，
热容密度与之一致）”“全节点事件判据（相比体积平均晚 37.25%）”“材料坐标（相比固定域 130.5 h
→ 51.2 h）”。没有 innovation 时，2.5 至少要有一条 contribution；否则 ⑨ 必须打回 ②，
不能写“本文不宣称创新”。

### Step 3.6: 创新面板（4 个默认视角，含闭合 + 1 个可选）

目的：避免第一条建模思路定终身，但**不是让 agent 多想几个点子**——每个候选都必须从
基线卡的失败模式出发，而不是从“我想用什么方法”出发。

1. 主 agent 先建 `_tmp/idea_panel/`，把题面、子问题拆解、Step 0 硬约束、**基线卡、失败模式清单**
   写进 `_tmp/idea_panel/brief.md`。子 agent 只读这份 brief，不读整个仓库。
   （用 Write 直接写 `brief.md` 即可，它会自动建目录；不要依赖 PowerShell `New-Item`——
   本次实测它在 `acceptEdits` 下会被拒绝，白费一轮。）
   建好 brief 后，按 `../_references/stage_discipline.md` 八建 `.fma_panel_lock`；收齐候选后先删锁，再写正式报告。
2. 用 Agent 工具并行启动 **4 个**子 agent（优先 `config/agents.json` 的
   `idea-mechanism` / `idea-data` / `idea-adversarial` / `idea-closure`；不可用时 general-purpose；
   默认 4 个**不同视角**，不是 4 份同题重答）：
   - A 机理（`idea-mechanism`）：模型漏了哪条物理通道、边界、耦合、尺度；
   - B 数据 / 辨识（`idea-data`）：哪个参数不可辨识、哪个数据没用上、误差怎么传到结论；
   - C 对抗 / 审稿（`idea-adversarial`）：专门攻击基线，找“如果成立就会让结论翻转”的假设，给最小修补；
   - D 闭合 / 耦合（`idea-closure`，**默认必开；纯优化/决策题可用 E 代替**）：先扫“同一物理量/几何被多个输入重复定义”
     （R(t) 与 ρ(C)、边界与物性、几何与守恒），提至少一条 `type=closure` 候选：
     朴素基线是什么、主闭合换成什么、一致性/差值怎么验证；**这是模型层贡献的主要来源**。
   - E 优化 / 决策（`idea-optimization`，**仅当题目真是优化/决策题**）：最优控制、鲁棒设计、
     调度、多目标、情景规划。非优化题不要默认开这个视角——它会产出题面没问的“优化烘房温度”。

   **默认 4 的理由**：前 3 个视角给机制/数据/对抗，闭合视角专门产出“模型层贡献”，
   避免 9 条候选全是参数假设、台账全 rejected、论文 2.5 没内容。四份候选如果**重叠 >50%**，
   或**可落地的不足 2 条**，再补 1 个「补位」agent（对立假设 / 另一学科视角）；总数 **≤5**。
   补位要针对缺口写 prompt，不要重复已有视角。连续一轮没有新主题就停（loop-until-dry）。
3. 每个子 agent 只写 `_tmp/idea_panel/<lens>.md`，每个方向固定七行：

   ```text
   失败模式：基线在什么条件下会错/不够？
   干预：加/换/证明什么？（机制 / 结构 / 判据 / 证据）
   可证伪命题：若……则……（要能被一个 test 推翻）
   预测增量：对哪个头条数字/决策，方向与量级；主答案预计怎么变、是否在护栏内
   验证：用什么数据/对照/负控制；什么结果算失败
   代价：实现时间、数据需求、是否违反硬约束
   类型与视角：mechanism/structure/criterion/evidence/closure + mechanism/data/adversarial/closure/optimization；
               这是 innovation（主模型增量）还是 contribution（朴素基线→本文结构）
   ```

   禁止写最终报告，禁止改 `code/`、`results/`。
4. 主 agent 读全部候选（3–5 份），按 Step 3.7 的**硬门槛**评分，选 1 个 core + 至多 1 个 supporting；
   其余方向各写一句「为什么不用」（不可验证 / 超时间 / 偏离题意 / 必要性不足）。
5. 子 agent 不可用（CLI 禁用 Agent）时，退回主 agent 自己按 A/B/C 三个视角各写 3 条，
   不要卡住阶段。

硬约束：

- 候选必须从失败模式出发，**不许从“我想用什么方法”出发**；工具名不是创新；
- 不得违反 Step 0 的题面硬约束，不得编数据；
- 采用前先做代价 / 收益判断：竞赛时间内能否实现、能否被 ③ 复核、④ 能否测出 delta；
- 子 agent 只写 `_tmp/idea_panel/`，正式报告与台账只由主 agent 写。
- 本机 headless `claude -p` 已实测可用 Agent 工具（2 个并行子 agent，约 32 s 全部完成）；
  若你的 CLI 版本禁用，按第 5 条退回，不要因此判阶段失败。

### Step 3.7: 评分与预注册（硬门槛，不是 1–5 分）

| 维度 | `kind=innovation` 通过条件 | `kind=contribution` 通过条件 |
|---|---|---|
| 必要性 | 去掉它，头条数字变化 ≥5%，或定性结论翻转 | 朴素基线确实错/不完整；去掉本文处理，一致性/差值证据消失或显著变差（**不要求头条数字变化**） |
| 可证伪 | 能写出一个可能失败的 test（对照/负控制/复算），不是“做灵敏度分析” | 同左 |
| 非显然 | 题面/文献没有直接给出，需要推导或对照才能看见 | 同左 |
| 可落地 | 数据可得，④ 能实现，⑥ 能检验；不超竞赛时间 | 同左 |
| 主答案护栏 | 主答案变化 ≤ `primary_guard.allowed_relative_change`；超出必须有 `independent_evidence` | **不适用**（基线不是主模型）；`core` 必须 false |
| 合规 | 不违反 Step 0 硬约束，不靠改口径/编数据 | 同左 |

`kind=innovation` 必须过**必要性 + 可证伪 + 主答案护栏**；`kind=contribution` 必须过
**贡献必要性 + 可证伪**，不套主答案护栏。一篇最多 **1 个 core innovation + 1 个 supporting
innovation + 3 个 contribution**。每个 adopted 必须写 `kill_if`：④ 测不到或测失败就降级，不许嘴硬。

**主答案优先于创新（仅 `kind=innovation`）**：如果创新让主答案大幅偏离基线、又没有独立
证据，正确结论是“这个创新不成立/模型没闭合”，不是“我的方法更精细”。温度 5 ℃ vs 空气
41 ℃ 就是前一种。

把**全部候选（含 rejected）**写进 `reports/INNOVATION_LEDGER.json`，schema 与示例见
`references/innovation-ledger.md`。最低要求：

- `panel.lenses` 至少 4 个不同视角，且 `closure` 与 `adversarial` 各至少要有一个
  （纯优化/决策题可用 `optimization` 顶替其中一项；不能两项都靠同一个 optimization 顶替）；
- `items` ≥3 条，且**至少 1 条模型层候选**（`type` ∈ `closure / structure / criterion`）；
  全是 mechanism/evidence 的台账会被 `check_innovation` 判“没有模型贡献”；
- `kind="innovation"` 的 adopted 最多 2 条（1 core + 1 supporting），每条必须有
  `core（true/false）/ baseline_id / failure_mode / intervention / claim / predicted_delta /
  test / kill_if / primary_guard`；
- `kind="contribution"` 的关键处理最多 3 条，**core 必须 false**，每条必须有
  `contribution（贡献是什么）/ baseline_is_naive（朴素基线为什么错）/
  contribution_evidence（验证证据或路径）`；不要求 primary_guard；
- 设计阶段**至少要预注册 1 条可望 adopted 的 contribution 或 innovation**（不保证通过；
  ④ 测失败可以 downgraded）。全 rejected + no_adoption_reason 不会让设计门禁报错，但 ③ 会
  退回补模型贡献、⑨ 会因 2.5 为空直接打回 ②；`no_adoption_reason` 只是诚实记录，不是
  “论文可以没有贡献”的许可证。

### Step 3.8: 写进报告

在 `ANALYSIS_MODELING_REPORT.md` 写「创新点与取舍」：

- **基线卡表**（Step 3.4）；
- **候选表**：`ID / 问 / kind / 类型 / 失败模式 / 干预 / 可证伪命题 / 预测增量或一致性证据 / 主答案护栏（innovation）/ 贡献证据（contribution）/ 验证 / 状态`；
- 采用项写清“为什么是它 + 代价 + 风险”，innovation 标明 `core` 还是 `supporting`，
  contribution 标明「模型特点与关键处理」；
- 未采用项各一句“为什么不用”（不可验证 / 超时间 / 偏离题意 / 必要性不足）；
- 只把 `kind=innovation` 且 `adopted` 且 `core=true` 的 1 项叫“核心创新”；其余 innovation
  叫 `supporting`，contribution 叫“模型特点与关键处理”；
- `kind=contribution` 的项写进「模型特点与关键处理」，每条写“朴素基线 → 本文处理 → 证据/差值”
  （如“体积平均 36.1272 h → 全节点 57.5702 h，晚 37.25%”“固定域 130.5 h → 材料坐标 51.2 h”）；
- **2.5 不能为空**：没有 innovation 时至少 1 条 contribution；禁止写“九项全 rejected /
  本文不宣称创新”——那是内部筛选记录，不是论文内容，也会触发 ⑫ 的“完全无创新”致命项；
- 不要用“创新点一/二/三”把 L0/L1 工作包装成创新。

收尾自检：

```bash
python lib/web/check_innovation.py --stage design
```

不过就当场修：补基线、补失败模式、补 test/kill_if，或把测不了的项改成 rejected。

### Step 4: 建模报告

在 `ANALYSIS_MODELING_REPORT.md` 中写出可交给代码阶段实现的完整方案。

每个子问题至少包含：

- 问题目标。
- 符号和变量。
- 模型假设。
- 目标函数。
- 约束条件。
- 求解方法。
- 输入输出。
- 代码实现要点。
- 结果校验方法。

公式要清楚到代码阶段能直接实现。算法描述要包含核心步骤、停止条件、复杂度或可行性说明。

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 数据处理方案
## 3. 符号说明
## 4. 问题一模型
## 5. 问题二模型
## 6. 问题三模型
    .... 
## 7. 灵敏度分析与检验方案
## 8. 代码实现任务清单
```

如果子问题数量不是 3 个，按实际题面调整章节，不要硬凑。

### Step 5: 给代码阶段的接口

在 `ANALYSIS_MODELING_REPORT.md` 末尾写一个“代码实现任务清单”，格式如下：

```markdown
## 代码实现任务清单

| 任务 | 输入 | 输出 | 方法 | 校验 |
| --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... |
```


## 质量要求

- 所有结论都能回到题面或数据。
- 不编造数据字段和数值。
- 不跳过歧义分析。
- 模型既要有数学表达，也要能被代码实现。
- 创新点必须能落到 `INNOVATION_LEDGER.json` 的可证伪增量（基线 → 失败模式 → 干预 → 实测 delta）；
  不为创新而创新，不把模型堆复杂；方法名（PSO/机器学习/材料坐标）不是创新。
- 若数据不足或题面不清，要明确记录风险和替代方案。

### 数学结构与理论精简（进代码前先"找结构"，避免纯蛮力/纯枚举）

竞赛高分常来自一个能缩小搜索/证明结论的结构性观察，而不仅是"枚举完整、数值对上"。每个子问题在设计数值方法前，先做一轮数学结构挖掘，在建模报告里给"理论精简"小节：

1. 找可证结构：单调性（最优解随参数单调 → 可二分/单调栈）、凸性/凹性、可分性（多目标能否解耦成子问题）、对称性、对偶、或题目域上的已知结论。能证的写成一两条引理/命题 + 证明要点，并说明它如何被用到（缩小搜索、保证全局最优、或给出剪枝依据）——"没被用到的定理"是装饰，不算数。
2. 几何/物理判据给解析依据：判据若用离散采样/枚举判定，给一个"为何采样充分/为何检查这些边界点就够"的解析论证（凸体、单调性、最坏情形），而不是只堆采样档数。
3. 诚实标注不可约处：若某子部分确无结构可挖掘、只能枚举/启发式，显式说明"为何不可被结构简化"，并给出你已利用的剪枝/上界依据。
4. 每个理论声明标"确定性"：哪些是可证命题（给证明要点）、哪些是数值发现的规律（标为观察/经验，不作定理宣称）——防"编一个看似定理的假命题"。证明要点必须步骤自洽、能被 4review 的 review-math 逐行复核。

别留给下游门禁 —— agent 的上下文到那时早没了，人也被拦在几十分钟之后。

### ① 题意契约锚点

```bash
python lib/web/check_contract.py      # 契约里每条 quote 还逐字指得到报告原文吗（与门禁同一函数）
```

不过就当场修（把 quote 换成新报告里的原文，或改引一个确实存在的段落）。

### ② 创新台账

```bash
python lib/web/check_innovation.py --stage design
```

不过就当场修：补基线/失败模式/test/kill_if；`kind=innovation` 再补主答案护栏，
`kind=contribution` 补 `contribution / baseline_is_naive / contribution_evidence`；
测不了的项写 rejected + 理由。尤其检查 innovation 的主答案护栏：如果创新会让主答案
大幅偏离基线又拿不出独立证据，先按模型没闭合处理，不要写成“创新点”。

### ③ 返修台账（被门禁退回过的轮次必做）

```bash
python lib/web/check_receipts.py
```

病灶：返修记录里写「§15.1 该句改『≤0.98%』」，而**那句话本身就是 `≤0.98%` 的一次出现** ——
拿"全文检索 ≤0.98%"当自检，记录自己把自己证明了。三例：`≤0.98%` /
`66600 s` / `M3`+`热供给` 的命中全在版本表或返修记录里，正文一处未改；另有一例是前缀碰撞
（回执要 `q4.moist_max_at_tend`，只加了 `..._minus_60s`，检索照样"通过"）。代价是 review 每轮
重查、每轮打回，白烧几十分钟。

**交 `reports/RECEIPT_LEDGER.json`**：回执里每一条都要交代，且 `applied` 的必须给
probes（一串「改完之后才会出现在正文里」的检索串）：

```json
{
  "schema_version": 1,
  "receipt": "runtime/quality/feedback/<run_id>/<hex>/gate_decision.json",
  "report": "reports/ANALYSIS_MODELING_REPORT.md",
  "items": [
    {"id": "MA-1", "disposition": "applied",
     "probes": ["χ_i = ρ_d(C_i) + C_i·ρ_d'(C_i)", "2|Ṙ|/R 均值/峰值 3.6×10⁻⁵–7.1×10⁻⁵ s⁻¹",
                "min_t[C_s − C_air] > 0", "必修披露清单（6 项）"]},
    {"id": "MA-2", "disposition": "partial",
     "probes": ["≤0.98%"], "remaining": "§9.9 T4 的量级 O(10%) 未写"},
    {"id": "MA-3", "disposition": "not_applied", "reason": "登记表待重排"}
  ]
}
```

四条硬规则：

1. **探针必须在「版本 / 修订 / 返修 / 变更」这类记录节之外命中** —— 记录里那句「已改为 X」不算证据。
2. ASCII 探针按标识符边界匹配 —— `q4.moist_max_at_tend` 不会被 `..._minus_60s` 撞上。
3. 复合判词逐小项给探针：回执的 `fix` 里编了 ①②③④ 的就是 4 个小项，`applied` 要给
   同样多条、互不包含的探针。MA-1 有 4 小项却只给一个探针就签了 `applied` ——
   下一轮门禁把剩下三项原样提出来，白烧一轮。*（分母取 `fix` 不取 `recheck`：后者含"复跑脚本"这类
   验证步骤，拿它当分母会逼你给验证步骤编假探针。）*
4. 没做就写 `not_applied` + `reason`，只做一半写 `partial` + `remaining` —— 诚实登记比谎报便宜
   （review 下一轮照样会查，但那时你要多烧一整轮）。**没做的事不能给探针。**

判据与本检查共用一份代码（`lib/web/receipt_ledger.py`），门禁侧读的是同一份台账，不另写一套。
