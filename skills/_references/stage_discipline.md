# 阶段通用执行纪律

> 本文件是以下五节纪律的唯一权威表述。
> 各阶段 SKILL 只写「引用 + 本阶段适用哪几条」，不复制正文 ——
> 复制必然漂移：同一条纪律在不同阶段措辞不同，新加的阶段直接没有。
> 若某阶段确实用不到其中某条，在该 SKILL 里写明豁免与理由，而不是不写。

---

## 一、增量返修

适用：任何会因上游回退或用户重跑而再执行一次的阶段。

返修时**不要从零重算全部** —— 那会把「只改了 Q5」放大成「Q1–Q5 全部重解 + 全部图表 + 全部指标重算」，
而全量重算是本链最贵的一步（单轮 30–150 分钟）。

1. 先做差异定位：读门禁回执里的 Fix 清单，明确要改的是哪个子问题、哪个量；再对比当前
   `results/*.json` 与上一版报告引用的数值，列出实际会受影响的子问题与派生量。
2. 只重算受影响的：与本次修复无关的解、指标、图表直接复用上一版产物，并在报告中标注
   「复用上一版（未受影响：〈理由〉）」。**判断依据必须写进报告**，不能凭感觉省略。
3. **受影响的必须完整重算**：不得沿用旧结论，**也不得只改报告数字而不重跑代码**。
   若重算后数值未变，如实写「重算后一致」。
4. 派生链要跟着走全：改了底层结果就必须重跑其下游
   （`derive_metrics` → `summary`/`calibers` → `make_xlsx` → `figdata`/`plots` → `result_contract build`）。
   漏跑下游会留下「报告数字与 `results/*.json` 不一致」的缺陷 —— 那正是审计最常抓、也最贵的一类返工。
5. 报告里单列一节「本轮增量重算清单」：哪些复用、哪些重算、为什么这样划分。
6. 方法与口径变更则回全量：若差异定位发现几乎全部子问题都受影响（判据口径、模型结构、
   几何口径、阈值定义等变更），回到全量流程，并在报告中说明原因。

### 1.1 探针与中间工具：保留，下轮先复用

上面讲的是复用产物；这条讲复用手段 —— 你自己写的探针/量测/实验脚本。

适用：任何会写这类脚本的阶段（数值验证、版式量测、图目检、合规扫描、接口核对…）。

1. 脚本一律写**项目内的 `_tmp/`**（名字带阶段与用途，例 `_tmp/mp_maxprinciple.py`），**收尾不要删** ——
   `_tmp/` 本来就不污染项目根；删掉只会让下一轮白纸一张。
   位置要按现状认，别只认一个名字：仓库里同时存在两种写法 ——
   `_tmp/`（⑩⑪⑮ 的探针在这里）与 `tmp/`（另有 **638 项**：②的 `an_probe_*.py`、
   `.before_r1` 快照、`_chk_manifest.py`…）。所以：
   · 新写的一律放 `_tmp/`（统一口径）；
   · 复用时要两个都看：`ls _tmp/ tmp/`（写成只认 `_tmp/` 会让 `tmp/` 下那一大批探针
     永远碰不到）；
   · **不要在系统临时目录**（`C:\tmp`、`%TEMP%`）写探针 —— 那样下一轮、换个人、换个工作区都找不到。
2. 重跑时**第一步先 `ls _tmp/ tmp/`**（连同上一轮自己报告里的「扫描范围 / 断言清单」一起看）：
   上一轮为哪些结论写过探针 ⇒ 先原样重跑它们（秒级），确认那些数在当前版本里是否仍成立。
3. 只对新出现或改过的对象写新探针 —— 别每次从零重写一遍。
   代价：⑩数学论证门禁 一轮写 8 个探针、跑 138 次 PowerShell、耗时 34.6 分钟，
   其中大半是重复劳动（根因正是要求"收尾清理"，下轮只能从零）；
   ⑪跨问一致性 同类（`_tmp/cross_probe1..9.py` + 30 KB 的 `build_cross_verdict.py`）。
4. 复用探针 ≠ 跳过复核：探针只是取证手段，判定仍要逐条对着当前版本做；
   探针结果与当前版本对不上时，以当前版本为准，并记为待修项。
5. 探针被替代/弃用时留一行注释说明（别只删掉）—— 否则下次没人知道"这个数是怎么来的"。

## 二、缩比预估

适用：任何会跑长计算的阶段。

**任何单次运行可能超过 5 分钟的计算脚本，必须支持 `--scale N`**（N 为 0.01–1 的缩放因子）：

- 把「规模」参数化（网格数 / 迭代次数 / 样本数 / 搜索宽度 / 重抽样次数）
- 缩比只改这个参数，不改方法 —— 得到的必须是同一个方法的粗略版本，不是另一个方法
- 跑缩比版并在 stdout 打印一行机器可读的预估：

  ```
  [SCALE_ESTIMATE] scale=0.05 elapsed=12.3s total_est=4100s
  ```

驱动在超时或假死时会从输出里抓这一行显示给用户，帮他判断「还值不值得等」。
抓不到就不显示预估 —— 不许凭经验编一个数字。

## 三、分段落盘

适用：同第二节。

**超过 5 分钟的计算必须切成 ≤5 分钟的片段，每段跑完立即落盘**（优先 `code/outputs/`）。

- 长搜索/长迭代尤其要这样：**把搜索切成多个 <90s 的片段逐段跑、逐段落盘**
- 每条子问题跑完立刻把结果与日志落盘，再进入下一条
- 这样即使进程被中断，已经算出来的部分仍在盘上，不会白跑

> **用现成的 `core.Checkpoint`，不要手工切片**。
> `code/core.py` 的 `Checkpoint(name, method, params, out_dir=None)` 就是为这一条写的：
> `save(state)` 落一片（`state["monitor"]` 另存为同名 `.monitor.json`），
> `restore()` 取回最后一片、没有则返回 `None`。
> 它**顺手把 §4.1 要求的 `.meta.json` 方法标记一起写了**，比手搓 `np.savez` + 手写 meta
> 少一处会漏的地方 —— 两条纪律一个工具。
>
> 这个类必须显式用起来：§3 只写了"要切片"、没写"用哪个"时，它会零调用。
> 长跑尤其要挂（本题 Q2/Q3 各 26 万步）：被掐断时盘上是完整的前若干片，
> 不是半份。

> 反例：前台跑长搜索被掐后，agent 半开连接挂死 26 分钟，什么都没留下。

## 四、方法标记与复用判定

适用：同第二节。

### 4.1 产物必须自带方法标记

**任何落盘到 `code/outputs/` 的中间产物，必须同时写一个同名 `.meta.json`**：

```json
{"_method": "q3_shrinkage",
 "_code_fp": "<驱动在 prompt 里注入的 code/ 指纹>",
 "_params": {"R_model": "R(t) 线性插值", "dt": "0.25/5", "N": 3200},
 "_produced_at": "2026-09-16T12:34:56", "_stage": "code"}
```

- `_method` 写一句话的方法名，不是文件名 —— 同一脚本换参数就是换方法
- `_params` 写会影响结果的关键参数
- `_code_fp` 抄驱动注入的那个值

### 4.2 复用判定：方法与参数都一致才跳

**重跑时先扫 `code/outputs/*.meta.json`，逐项比对：

| 比对结果 | 动作 |
|---|---|
| `_method` 与 `_params` 完全一致 | 可复用该产物，报告中标注「复用（方法/参数未变）」 |
| 方法或参数变了 | 该产物作废，必须重算，报告中标注「作废旧产物（方法变更：A → B）」 |

不得因为「文件在、名字对」就复用 —— 这正是方法从 A 换成 B 之后误用旧产物的来源。

## 五、返修只动清单内

适用：任何可能被门禁/审计回执退回的阶段。

按回执返修时，改动范围必须严格等于回执清单。四条硬纪律：

1. 只改回执点名的位置；回执里「可放行部分／保留，勿重写」明列的内容逐字不动。
2. 改前留副本、改后 diff**：`cp <被改文件> tmp/<名字>.before` → 改完 `diff` 出**全部改动行，
   逐行确认每一处都对应回执的某一条；清单外的改动一律回退。
   这是唯一能真正挡住「顺手把原本正确的地方改坏」的机械手段 —— 只靠「注意别改错」的自觉挡不住。
3. 逐条执行回执给的复验方式并把真实输出写进自查**（如 `grep -c "…"` 应为 N 处、重跑某脚本复算某数）。
   禁止只写「已修正/已删除」而无输出 —— **自查行必须来自命令输出，不是来自意图。
4. 返修途中发现的新问题不顺手改，列入报告末尾「本轮新发现（未改）」交下一轮门禁；
   否则改动范围失控、评审无法逐条对账。

> 回执给的替换句/式必须逐字采纳（或写成逐字等价的表述），禁止意译重述 ——
> 意译是修复时引入新错误的根源（把门禁给的正确句子意译后会写反符号方向）。

每个阶段的典型踩坑点**（各 SKILL 自己补一条具体的）：

| 阶段 | 本阶段的「改 A 坏 B」长什么样 |
|---|---|
| 3analysis | 同一个量在验算表/判据汇总/口径表/必报字段多处重复，改一处必须同步全部引用处 |
| 5coding | **改一处数值会影响下游全部派生量，顺手改动会被审计当成新缺陷抓出来 |
| 9Paper-writing | 同一个量在摘要/正文/图注/表/后文引用里反复出现，改一处不改其余即新硬错误 |
| 14Layout-and-format | 版式改动尤其容易"顺手改了别的"：改一处必须重新量一次 `measure_layout.py` |

（其余阶段退回时同样适用本节的四条；上表只是常见形态，不是封闭清单。）

## 六、阶段收尾自检（自己产的东西，自己在交出去之前对一遍）

适用：所有只审不改的门禁阶段（4review / 5Result-credibility-audit / 10Math-proof-gate / 11Cross-question-check /
15Verification / 12Rubric-final），以及会产出互相引用的多个文件**的生产阶段（3analysis 的
`TASK_CONTRACT.json` + `ANALYSIS_MODELING_REPORT.md` 是最典型的一对）。

### 6.1 门禁：**先落骨架，再深挖

开工第一步就写报告与裁决侧车，`status` 置 `UNVERIFIED`、`issues: []`；之后每查完一维回填一次。

门禁的活儿（独立子 agent、拿题面公式复算、逐页看图）极容易吃光整段时间，
而产物"最后才写" —— 一旦跑到没气，现场就是一片空白：

- 驱动只能报「阶段未成功完成：failed」，读不出任何结论
- 人看不出它已经查出了什么，无法据此决策
- 连"只补裁决侧车就放行"那条路都走不了（报告根本不在），只能整段重跑

先落骨架之后，最坏情况变成「报告在、裁决是 UNVERIFIED」 —— 同样是黄灯，但报告可读、
驱动报错从"阶段没跑完"变成"裁决未完成"（指得准）、且能只补侧车。

这不是「先交差再补」的许可。骨架是占位**不是结论：每查完一维必须回填，
`status` 只有在**所有必查项都真的查过之后才能改。骨架本身不构成任何检查结论。

骨架的报告末尾那行「整题门禁裁决」不许写三个真裁决词里的任何一个
（`APPROVED` / `REVISE_HARD` / `REVISE_SOFT`）—— 写成 `（待填）` 就够。
代价：写了「`## 整题门禁裁决：REVISE_HARD（占位，未定型）`」⇒ 驱动的 Markdown 解析只认那个状态词、
不认括号里的说明 ⇒ 与侧车的 `UNVERIFIED` 撞成「裁决冲突」⇒ 整链停机（黄灯文案还是
「未获得当前版本的明确有效裁决」，读起来像内容问题，其实是暂停留下的雷）。
驱动侧已加固（侧车 `UNVERIFIED` ⇒ 判"未完成"、不当冲突），但占位行仍不要写真裁决词 ——
两层保险，缺一层就再卡一次。

本条必须写进各门禁 SKILL 的「执行方式/工作流」第 1 步**，不能只留在这份参考文件里。
反例：3Modeling-review-gate 的头部引用了 §6.1，但 `## 执行方式` 里"汇总写报告"排在最后一步 ——
agent 照着执行方式做，就把骨架漏了。规则写在头部没人看，写在它真正会读的那一步才生效。

**关键路径原则：门禁里只有报告是不可替代的，你的复算脚本全都有替代品（子 agent 已经在做）。
所以别在主会话自造求解器去验子 agent 的结论 —— 那是把可替代的活排在不可替代的活前面。
同例：review 主 agent 自写 ODE 求解器并反复调试，吃掉本阶段大半时间，四个维度一个都没定稿。

### 6.2 生产阶段：交出去之前，自己把「互相引用的文件」对一遍

一个阶段产出多个互相引用的文件时（契约引用报告、图注引用结果、摘要引用正文），
它们是以必然互相矛盾的顺序写出来的 —— 后写的那个一改，先写的那份引用就失效。

所以收尾前自己跑一遍那个对账**，别留给下游门禁：

| 阶段 | 收尾自检 |
|---|---|
| 3analysis | `python lib/web/check_contract.py` —— 契约里每条 `quote` 是否还逐字指得到报告原文（与门禁**同一个函数**） |
| 3analysis（被退回过的轮次） | `python lib/web/check_receipts.py` —— 返修台账（见 6.3） |
| **全部门禁**（③⑤⑦⑧⑩⑪⑫⑮） | `python lib/web/check_verdict.py --stage <阶段id>` —— **交裁决侧车之前跑一遍 |

那条命令做的是：拿驱动同一套函数**（`content_quality.enforce` + `workflow_quality.read_verdict`）
校验你这就要交出去的 `reports/<报告>.verdict.json`，逐条说清哪里会被打回（缺哪个必查 ID、
哪条 evidence 的 quote 在源文件里找不到、哪个 failed 检查没关联 issue、报告裁决行与 JSON 是否冲突）。
退出码 0 = 规则都过（**不代表裁决是好消息，status 可能是 NEEDS_FIX）。

为什么必须跑**：⑮验收 在 45 分钟里花了 **10 次工具调用去读驱动源码**
（`lib/web/workflow_quality.py` 读 3 次、grep `read_verdict` / `verdict_conflict`，还试着 import 驱动模块），
只为确认自己的侧车会不会被打回。规格在 `docs/CONTENT_QUALITY.md` 里是**散文，
而校验器就在这个仓库里 ⇒ 它去读了源码。跑一条命令就能替代那一整段摸索。

它还能认出一种你自己的错处解决不了的坏法：侧车引用的文件在侧车写成之后**又被下游改过
（例如 ⑭ 排版改了 `paper/sections/*.tex`）⇒ 报的是「会被打回」而实际是过期，
正确处置是本门禁重判，照着"补 JSON"去改只会把一条正确的判词改坏。

不过就当场修（把 quote 换成新报告里的原文，或改引一段确实存在的），不要写一句
"已知不一致"就交出去 —— 下游门禁一样会拦，但你那时的上下文已经没了。

### 6.3 返修台账：**返修记录不许自证**

被门禁退回过的轮次，报告里会长出一张「本轮返修复验记录」表。这张表是循环的最大来源 ——
因为它写下的每一句「已改为 X」本身就含 X：

> 表里写「③ §15.1『偏差 ≤0.4%』改为 **≤0.98%**」
> → 拿「全文检索 ≤0.98%」当自检 → 记录自己把自己证明了 → 交出去 → review 一查，
>    §15.1 正文还是 ≤0.4% → 再退回 → 下一轮重来。

典型三例（经独立字符串计数复核）：

| 回执要求 | 记录里写 | 正文实际 |
|---|---|---|
| §15.1「≤0.4%」→ ≤0.98% | 「③ 已改」 | 正文仍 ≤0.4%；`≤0.98%` 三处命中全在版本表/记录里 |
| §15.2 改「自 66600 s 起」 | 「① 已改」 | `66600` 的命中全在版本表/记录里，§15.2 正文 0 |
| §2 A3 / §9.9 T4 补 `M3`、`热供给` | 「已做」 | 两串只在记录里出现，正文 0 |

还有一类是前缀碰撞：回执要 `q4.moist_max_at_tend`，实际只加了
`q4.moist_max_at_tend_minus_60s` —— 而回执给的「检索 ≥1 命中」照样通过。

**所以交 `reports/RECEIPT_LEDGER.json`**，回执里每一条都要交代；`applied` 的必须给
probes：一串「改完之后才会出现在正文里」的检索串。四条硬规则：

1. **探针必须在「版本 / 修订 / 返修 / 变更」这类记录节之外命中。** 记录里那句「已改为 X」不是证据。
   —— 检查器按标题栈判定：`### 15.1 本轮返修复验记录` 挂在 `## 15. 版本与修订历史` 下，两级都算记录区。
2. ASCII 探针按标识符边界匹配，不许被更长的串撞上（`q4.moist_max_at_tend` 别被 `..._minus_60s` 撞上）。
3. 复合判词要逐小项给探针。 回执的 `fix` 里编了 ①②③④ 的，就是 4 个小项；
   `applied` 必须给同样多条、互不包含的探针。MA-1 有 4 小项却只给了一个探针
   （只对应其中 P5 那一项）就签了 `applied` —— 下一轮门禁把剩下三项原样提出来，白烧一轮。
   *（分母取 `fix`，不取 `recheck` —— 后者常把「复跑脚本」「复算常数」也编号进去，
   拿它当分母会逼你给验证步骤编一个假探针。）*
4. **没做就写 `not_applied` + `reason`，只做一半写 `partial` + `remaining`。没做的事不能给探针。**
   诚实登记比谎报便宜 —— review 下一轮照样会查，但谎报要多烧一整轮。
